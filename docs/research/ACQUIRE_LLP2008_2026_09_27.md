## 6. Findings that outlive this task

1. **F15 is still open and it is why this task failed.** `docs/evidence/FAILURE_MODES.md` F15 recorded India
   Code's `robots.txt` answering **502** "continuously since ~21 August", concluded the fail-closed
   gate is *correct*, and named the missing piece: **nothing in this repository re-checks.** Today
   the same endpoint answers **500**. Five weeks on, the proposed
   `scripts/retry_blocked_sources.py` does not exist, so a transient became permanent exactly as
   predicted. This is now blocking body 4 of the plan, not just S-002.

2. **`scripts/ingest_act.py` never consults `checker/robots.py`.** It imports `USER_AGENT` and
   `ssl_context` from it and fetches with bare `urllib` — no `Fetcher`, no `allowed()`. So the
   moment someone pastes a confirmed actid into the register, the ingest will fetch straight through
   a gate that is currently shut, and nothing will say so. `CLAUDE.md`'s repository map calls
   `checker/robots.py` *"Robots + TLS enforcement in the fetch path; fails closed"* — true of the
   TLS half, **not true of the robots half on the statute path.** (Not fixed here: editing that file
   was out of scope for this task.)

3. **The four accessibility states have no slot for 5xx.** `ACCESSIBLE` / `BLOCKED` / `UNREACHABLE` /
   `NOT_FOUND` cover 2xx, 403, no-answer and 404. A 500 is an *answer*, so `UNREACHABLE` would be
   the exact 2026-08-21 conflation the policy forbids — and `UNREACHABLE` is the only retryable
   class. It is recorded as `BLOCKED` with `http_status=500`, which keeps the record factual, at a
   cost worth naming: **`BLOCKED` means never-retry-automatically, which is the wrong instruction
   for a server fault.** The 500 in the status field is what makes the mislabel visible instead of
   silent. A fifth state (`SERVER_ERROR`, retryable with backoff) would fix it properly.

4. **`summary()` keys `never_retry_automatically` by URL, not URL+method.** `https://indiacode.gov.in/`
   was `BLOCKED` on HEAD and `ACCESSIBLE` on GET; the URL lands in `never_retry_automatically`
   anyway. Harmless here — it is a control probe — but it means a URL that works under one method can
   be flagged never-retry by another.

5. **The 30-day escape hatch does not rescue this.** RFC 9309 lets a crawler fall back to a
   cached ruleset once `robots.txt` has been unreachable for over 30 days. It does not apply: it is a
   *MAY*, `checker/robots.py` implements no cache and no window, and the continuity it depends on —
   "since ~21 August" — is approximate and spans a change from 502 to 500, so the threshold cannot
   be shown to have been crossed. Recorded so nobody reaches for it as a shortcut.

6. **Two RFC subsection numbers are in circulation and neither was read.** This report and
   `ACQUIRE_COMP2002_2026_09_27.md` cite **§2.3.1.3** and **§2.3.1.4** respectively for the same
   proposition. The RFC text was not fetched by either (it is not on the permitted host and was not
   worth a detour), so **the subsection number is UNVERIFIED in both** and is not load-bearing: the
   proposition — a 5xx `robots.txt` is a full disallow, with a 30-day cache fallback — is
   independently implemented in `checker/robots.py:rules_for_status()`, which is this repository's
   authority regardless of where the RFC puts it. Anyone quoting a subsection externally should read
   RFC 9309 first.
